* Beadwork (bw) -- Agent Issue Tracker on a br-Compatible Store

Beadwork is a dependency-aware issue tracker for human and agent workflows,
stored in the same `.beads/` SQLite + JSONL format as
[[https://github.com/steveyegge/beads][beads]] and
[[https://github.com/Dicklesworthstone/beads_rust][beads_rust]] (br), so both
tools can read the same database.

It started as a Common Lisp reimplementation of br and kept the storage layer
compatible. What it adds is the workflow layer agents actually run on:
=bw batch= (atomic multi-operation writes with idempotency and dry-run),
=bw session= (handoff notes and breadcrumbs that survive context restarts),
=bw doctor= (a status-doc <-> issue sync gate), and source-repo scoping so many
repositories can share one tracker.

**CLI Name:** =bw=

**Status:** Beta -- dogfooded daily across the cogen-meta repositories (700+
issues, 50+ sessions).

* Installation

**Requirements:**
- SBCL (or other ASDF-compatible Common Lisp implementation)
- Quicklisp

**Setup:**

1. Clone or symlink beadwork to your Quicklisp local-projects:

#+begin_src sh
# Option 1: Clone
cd ~/quicklisp/local-projects
git clone https://github.com/yourusername/beadwork.git

# Option 2: Symlink (if working on it)
ln -s /path/to/repos/beadwork ~/quicklisp/local-projects/beadwork
#+end_src

2. Build the binary:

#+begin_src sh
cd ~/quicklisp/local-projects/beadwork
make build
#+end_src

3. Install (optional):

#+begin_src sh
make install  # Installs to ~/.local/bin/bw
#+end_src

* Usage

**Initialize a new beads project:**

#+begin_src sh
bw init
# Or in a specific directory:
bw init -p /path/to/project
#+end_src

**List issues:**

#+begin_src sh
bw list                    # Issues for the repo detected from cwd
bw list --all-repos        # The whole project
bw list --status closed    # Filter by status
bw list --priority P1      # Filter by priority
bw list --type bug        # Filter by type
bw list -a jboehland     # Filter by assignee
#+end_src

`list` and `ready` filter to the repo found by walking up from the current
directory to the nearest `.git/`, and both print that scope in their header. At a
meta-project root the detected repo is the root itself, not "everything" -- use
`--all-repos` to see sibling repos. An issue that "does not exist" is usually
just outside the current filter.

**Create issues:**

#+begin_src sh
bw create -t "Fix the bug" -d "Description here" --repo my-repo
bw create -t "New feature" -T feature -p P1 --repo my-repo
bw create -t "Child task" --parent bd-abc   # inherits the parent's repo
#+end_src

`--repo` names the board the issue belongs to; it is mandatory at top level so
nothing lands in the unscoped `.` bucket. A child created with `--parent`
inherits the parent's repo unless `--repo` says otherwise.

**Update issues:**

#+begin_src sh
bw update bd-123 -t "New title"
bw update bd-123 --status in_progress
bw update bd-123 -p P0
bw update bd-123 --repo cogen-cli                # move it to another board
bw update bd-123 -n "Replacement notes"         # replaces the notes field
bw update bd-123 --append-notes "More evidence" # keeps the existing notes
#+end_src

`--repo` has two jobs depending on the command: on =create= and =update= it
**sets** the issue's source repo, on =list=, =ready=, =show= and the other read
commands it **filters** by it. The help text says which one applies. Omit it on
=update= and the board stays as it was.

=update= and =batch= can move an issue between boards; that is how an unscoped
or misfiled issue gets fixed without touching its status.

**Close/reopen issues:**

#+begin_src sh
bw close bd-123 -r "Fixed the issue"
bw reopen bd-123
#+end_src

**Show issue details:**

#+begin_src sh
bw show bd-123
#+end_src

=show= also lists the issue's graph neighborhood (parent, children, blocking
dependencies, and dependents) as a "Relationships" block. With
=--format json= the same information appears under =parent=, =children=,
=dependencies=, and =dependents=.

**Ready (unblocked) issues:**

#+begin_src sh
bw ready
#+end_src

**Dependencies:**

#+begin_src sh
bw dep add bd-child bd-parent    # bd-child is blocked by bd-parent
bw dep remove bd-child bd-parent
bw dep list bd-123               # bd-123 depends on / is blocked by ...
#+end_src

*Direction matters:* a dependency is stored as =(dependent, depends-on)=, so
=source= depends on =target=. In a =bw batch= link op, =source= is the
blocked/child side and =target= is the blocker/parent side:

#+begin_src json
{ "op": "link", "source": { "id": "bd-X" }, "target": { "id": "bd-Y" }, "relation": "blocks" }
#+end_src

makes =bd-X= blocked by =bd-Y= (not the other way around).

Relation vocabulary: =blocks=, =parent-child=, =conditional-blocks=,
=waits-for=, =related=, =discovered-from=, =replies-to=, =relates-to=,
=duplicates=, =supersedes=, =caused-by=. Only =blocks=,
=conditional-blocks=, =waits-for=, and =parent-child= affect =bw ready=
and =bw blocked=.

**Batch operations:**

#+begin_src sh
bw batch --file /tmp/batch.json            # create/update/link/comment atomically
bw batch --example                         # print a sample payload
bw batch --file /tmp/batch.json --dry-run  # validate + simulate, then roll back
#+end_src

=--dry-run= runs the whole batch in a transaction and rolls it back: nothing
is persisted and the idempotency key is neither read nor written.

Each =create= op takes a =repo= field; =--repo= on the command line is the
default for ops that omit it. Each =update= op takes one too, and there it
*moves* the issue to that board -- batch is the way to rescope a dozen issues
in one transaction.

**Labels:**

#+begin_src sh
bw label add bd-123 important
bw label remove bd-123 important
bw label list bd-123
#+end_src

**Search issues:**

#+begin_src sh
bw search "login bug"        # LIKE search on title + description
#+end_src

**Statistics:**

#+begin_src sh
bw stats                      # Aggregate counts by status, priority, type
bw stats --format json        # JSON for programmatic use
#+end_src

**Session management:**

#+begin_src sh
bw session start               # Create or resume session (shows handoff)
bw session status              # Active issue, uptime, last breadcrumb
bw session work bd-123        # Set active issue for this session
bw session action "Found root cause"  # Breadcrumb (auto-comments)
bw session end --notes "Next: dark mode"  # End with handoff
bw session list                # Recent 20 sessions (--all, --limit N,
                               #   --active, --agent-id X, --format json)
bw session show                # Last session in detail (handoff notes)
bw session show S-abc          # A specific session
#+end_src

**Comments:**

#+begin_src sh
bw comment add bd-123 "Fixed the token refresh"
bw comment list bd-123
bw show bd-123                # Single-issue view also prints the comments
#+end_src

Comments are exported to =issues.jsonl= and imported back, so a comment is
durable evidence, not a scratch note local to one machine.

**Delete issues:**

#+begin_src sh
bw delete bd-123              # Confirms before deleting
bw delete bd-123 -f           # Skip confirmation
#+end_src

**Blocked issues:**

#+begin_src sh
bw blocked                     # Issues blocked by unclosed dependencies
#+end_src

**Sync (JSONL import/export):**

#+begin_src sh
bw sync --direction export  # Export to issues.jsonl
bw sync --direction import # Import from issues.jsonl
#+end_src

**Output formats:**

All commands support =--format= option:

#+begin_src sh
bw list --format json     # JSON output
bw list --format plain    # Plain text
bw list --format rich     # Rich terminal output (default)
#+end_src

* Configuration

Beadwork looks for a =.beads/= directory starting from the current directory and walking upward. The directory should contain:

- =beads.db= -- SQLite database
- =config.yaml= -- Configuration (optional)
- =issues.jsonl= -- JSONL export for git sync

* Development

**Build from source:**

#+begin_src sh
cd repos/beadwork
make build      # Builds bin/bw
make test       # Builds bin/bw, then runs the suite (~25s cold)
make clean      # Clean build artifacts
#+end_src

=make test= builds first on purpose. The CLI suite (test/cli.lisp) spawns
=bin/bw= as a subprocess for every top-level command and asserts stdout,
stderr, exit code, and the resulting database state -- so the binary *is* part
of the test surface, and grading a stale one would be a silent failure. Each
case runs against its own =--db= directory under =/tmp=.

A focused run (=make test-eval EVAL="..."=) skips the rebuild; if it reaches a
CLI test whose =bin/bw= is older than =src/=, the harness errors with
"bin/bw is older than src/" rather than testing old code.

* Durability

`.beads/beads.db` is the working store and is **gitignored**;
`.beads/issues.jsonl` is the durable, git-tracked record. =bw sync --direction
export= is the only thing that copies one to the other, and nothing warns you
when it is stale.

The JSONL carries each issue's labels, dependencies, and comments. Comments use
the same =comments= array as =br=: =id=, =issue_id=, =author=, =text=, and
=created_at=. Import is additive for comments: it reconstructs missing ones and
refreshes the same id, but never deletes a local comment that is absent from the
file.

End every session that writes issues with:

#+begin_src sh
bw sync --direction export      # beads.db -> issues.jsonl
# commit .beads/issues.jsonl in the metadata repo
#+end_src

An export that finds a timestamp it cannot parse still writes the file, prints a
warning for every lost field, and exits 1. =--direction import= upserts from the
JSONL (=INSERT OR REPLACE=): no deletes, no timestamp guard, so never import a
file you have not looked at.

* Interoperability with br

Beadwork implements the core of the original beads/br feature set and uses the
same database schema, so you can use =br= to work on an issue and =bw= on
another, both reading/writing the same =.beads/beads.db=. JSONL export/import is
compatible.

Known asymmetries:

- A stored timestamp =bw= cannot parse (for example an old 10-digit fractional
  second) makes =br= refuse the whole command, while =bw= exports that field
  without a value. =bw sync= reports such rows; fix them, then re-export.
- =bw= omits tombstones from =issues.jsonl=, so =br doctor= reports a
  DB-vs-JSONL count difference that is expected, not corruption.

Note: Beadwork does not implement all features of br -- it's a ground-up CL
implementation with a focused scope for human and agentic workflows.
